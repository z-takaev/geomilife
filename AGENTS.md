# Правила работы с проектом

## Общение и порядок работы

- Всегда отвечать на русском языке, кратко и по существу.
- Все Markdown-инструкции (`*.md`) писать на русском языке.
- Перед реализацией задачи сначала изучить существующий код, сформулировать краткий план и согласовать его с пользователем. Переходить к реализации без дополнительного согласования только по явной просьбе пользователя.
- Если для корректной реализации не хватает существенной информации, сначала задать уточняющие вопросы. Не принимать решения, заметно меняющие поведение системы, без согласования.
- Не изменять файлы, не относящиеся к текущей задаче, и сохранять уже существующие изменения пользователя.

## Команды и инструменты

- Artisan-команды запускать только через Sail: `sail artisan ...`.
- Composer-команды запускать только через Sail: `sail composer ...`.
- npm-команды запускать только через Sail: `sail npm ...`.
- Laravel-классы и другие поддерживаемые Laravel-сущности создавать подходящей командой `sail artisan make:*`, а не вручную. Если специализированного генератора нет, использовать `sail artisan make:class`.
- Для безопасной проверки форматирования без изменения файлов использовать `sail composer format:check`.
- После изменения кода запускать `sail composer format`.
- После изменения миграций, связей, аксессоров, мутаторов или query scope моделей запускать `sail artisan ide-helper:models --nowrite`.
- Команды с потенциально большим диагностическим выводом ограничивать по объёму через `head -c` или `tail -c`. Не ограничивать таким способом тесты, форматирование и другие команды, для которых важно сохранить корректный код завершения.

## Процесс разработки и тестирование

- Изменения поведения разрабатывать по TDD: сначала написать тест, описывающий ожидаемое поведение, и только затем изменять рабочий код.
- Сначала запускать только новый или непосредственно затронутый тест через `sail artisan test <путь>` или `sail artisan test --filter=<имя>`. Перед реализацией убедиться, что новый тест падает по ожидаемой причине.
- Не изменять существующие тесты под реализацию ради устранения их падений. Изменять ожидаемое поведение тестов можно только после явного подтверждения пользователя.
- Реализовывать минимальный объём кода, необходимый для прохождения теста. Рефакторинг выполнять только после успешного прохождения целевого теста и затем запускать его повторно.
- После реализации запускать `sail composer format`, затем повторно запускать затронутые тесты.
- После завершения изменений кода последним действием запускать `sail composer test` и убеждаться, что все тесты успешно пройдены.
- Для изменений только документации, не влияющих на исполняемый код и конфигурацию, форматирование и тесты не требуются.

## PHP и качество кода

- Во всех PHP-файлах использовать `declare(strict_types=1);`.
- Классы, не предназначенные для наследования, объявлять с модификатором `final`. Это относится, в частности, к контроллерам, сервисам, Action-классам, командам и слушателям.
- Использовать строгую типизацию параметров, возвращаемых значений и свойств там, где это возможно.
- Не выполнять явное приведение типов без необходимости. Использовать его только на границах системы, при нормализации внешних данных или когда тип невозможно гарантировать иным способом.
- Давать классам, методам и переменным понятные названия из общепринятой практики. Избегать как слишком общих, так и неоправданно длинных названий; учитывать контекст использования.
- Писать чистый, лаконичный код без скрытого поведения и преждевременных абстракций.
- Логически разделять блоки внутри методов пустыми строками.
- Не добавлять комментарии, пересказывающие код. Комментарий допустим только для объяснения неочевидной причины, ограничения, компромисса или обходного решения.
- Создавать трейт только для стабильной одинаковой технической логики, используемой как минимум в трёх несвязанных классах. Один трейт должен иметь одну ответственность. Размещать трейты в `app/Traits`; не использовать их для бизнес-логики, подмены наследования, внедрения зависимостей или хранения несвязанных вспомогательных методов.
- Не использовать Laravel-атрибуты. Конфигурацию Laravel-классов задавать традиционными свойствами и методами.
- Не дублировать значения и поведение по умолчанию явной конфигурацией, если настройки проекта уже обеспечивают нужное поведение.

## Архитектура

- Оставлять контроллеры простыми и тонкими, без бизнес-логики.
- Бизнес-логику отдельной предметной области размещать в Service-классах в `app/Services`, когда выделение такого слоя действительно оправдано.
- Одиночную самостоятельную операцию оформлять как Action-класс в `app/Actions`. Service объединяет логику предметной области, Action выполняет одну конкретную операцию.
- Repository-классы в `app/Repositories` использовать только для действительно сложного, повторно используемого или заменяемого доступа к данным. Не создавать обёртки над простыми Eloquent-запросами.
- DTO-классы в `app/DTO` использовать для осмысленной типизации входных и выходных данных, а не для простой передачи нескольких значений.
- ViewModel-классы в `app/ViewModel` использовать для нетривиальной или повторно используемой подготовки данных к отображению. Не создавать ViewModel для простого вызова `compact()`.
- Внутри архитектурных слоёв группировать классы по бизнес-сущностям, например `app/DTO/Orders/CreateOrderDto.php`.
- Добавлять к именам архитектурных классов постфикс их назначения: `Dto`, `Service`, `Action`, `Repository`, `ViewModel`.
- В `app/Support` хранить `helpers.php` с глобальными функциями и общие технические сущности, не относящиеся к конкретной бизнес-области. Общие трейты, исключения и другие сущности группировать по соответствующим поддиректориям.
- PHP Enum размещать в `app/Enums`. Имена case и их строковые значения писать в верхнем регистре, например `case CREATED = 'CREATED';`.
- Не создавать архитектурные слои для простых случаев, если они только усложняют структуру.
- Не допускать дублирования кода. Если дублирование обоснованно, заранее объяснить причину и получить подтверждение пользователя.

## Eloquent

- Верхнеуровневые запросы к Eloquent-моделям начинать с `Model::query()`.
- Запросы через связи начинать с метода связи, например `$order->items()`, поскольку связь уже является построителем запроса.
- Следить за количеством запросов и предотвращать N+1 с помощью осмысленной eager loading-загрузки.
- В моделях соблюдать порядок секций: трейты; константы; свойства конфигурации Eloquent (`$timestamps`, `$table`, `$fillable`, `$hidden`, `$appends`, `$with`); метод `casts()`; метод `booted()`; переопределения поведения Eloquent; связи; query scopes; аксессоры и мутаторы; публичные методы предметной области; методы интеграций; защищённые расширения трейтов; приватные вспомогательные методы.

## Денежные значения

- Денежные значения в моделях и бизнес-логике представлять объектом `App\Support\Values\Money`.
- Хранить денежные значения в базе данных целым количеством копеек и преобразовывать их через `App\Support\Values\Casts\MoneyCast`.
- Не выполнять бизнес-расчёты над денежными значениями как над необёрнутыми `int`, `float` или строками. Использовать методы `Money`.
- Внешние значения преобразовывать в `Money` на границе системы. Не использовать `float` для денег.
- Цены в пользовательском интерфейсе отображать целыми рублями без копеек через `Money::format()`.

## Blade, HTML и CSS

- Не размещать бизнес-логику, запросы, расчёты и подготовку сложных структур в Blade-шаблонах. Передавать в шаблоны заранее подготовленные данные.
- При передаче данных из контроллеров в Blade использовать `compact()`.
- Весь пользовательский текст в Blade, включая текстовые значения HTML-атрибутов, оборачивать в `__()`.
- Логически разделять крупные HTML-блоки в Blade-шаблонах пустыми строками.
- Использовать семантические HTML-элементы и валидную вложенность. Не вкладывать интерактивные элементы друг в друга.
- Для изображений задавать содержательный `alt`, а для декоративных изображений — пустой `alt=""`.
- У полей форм должно быть доступное название через связанный `label` или подходящий ARIA-атрибут. Кнопкам задавать корректный `type`.
- Не использовать ссылку вместо кнопки для действия и кнопку вместо ссылки для перехода.
- Значения HTML-атрибутов `id` должны быть уникальными в пределах страницы.
- Допускается указывать `width` и `height` изображения для фиксации его исходных пропорций и предотвращения сдвига макета. Визуальные размеры и адаптивность задавать CSS.
- Использовать CSS-переменные, объявленные в `:root` файла `public/assets/css/styles.css`, и не дублировать их литеральные значения без необходимости.
- Для цвета текста использовать переменные `--text-black`, `--text-secondary` и `--text-white`.
- Переменные `--black` и `--white` использовать только для нетекстовых элементов: фонов, границ, заливок, обводок и других декоративных свойств.
- Директория `/template` содержит исходный HTML-шаблон. Использовать его как основу, переносить нужные элементы в Laravel, Blade и Livewire и адаптировать под требования проекта.

## Livewire

- Для нетривиальных форм с несколькими полями, собственной валидацией или повторным использованием создавать отдельный класс, наследующий `Livewire\Form`, через `sail artisan livewire:form`. Не создавать Form-класс для одного-двух простых полей без дополнительной логики.
- Свойства форм, сохраняемые в Eloquent-модель, называть в `snake_case` в соответствии с колонками базы данных, чтобы результат валидации можно было передавать в модель без переименования ключей.
- Валидацию задавать традиционным методом `rules()`, без PHP-атрибутов.
- В Livewire-компонентах соблюдать порядок методов: инициализация (`boot()`, `mount()`); хуки изменения состояния (`hydrate()`, `updating*()`, `updated*()`); публичные действия; `render()`; завершающие хуки (`rendered()`, `dehydrate()`); защищённые методы конфигурации Livewire (`queryString()`, слушатели, валидация); приватные вспомогательные методы.

## Медиафайлы и Filament

- Всю работу с загрузкой изображений выполнять через `spatie/laravel-medialibrary`.
- Для загрузки изображений в Filament использовать `App\Filament\Forms\Components\SpatieMediaLibrary`.

## Окружение и безопасность

- Проект развёрнут на shared-хостинге Beget. Планировщик запускается cron-командой `schedule:run` раз в минуту, а обработчики очередей запускаются через Laravel Scheduler. Не проектировать решение, требующее постоянно работающего queue worker, без отдельного согласования.
- В локальной среде не создавать дополнительные защитные сценарии и резервные копии только ради сохранения текущих данных базы. Потеря локальных данных допустима после явного подтверждения операции пользователем.
- Для установки и сброса проекта использовать `sail artisan project:install` и `sail artisan project:refresh`. Для тестовых данных передавать `--factories`. Эти команды запускать только после явного подтверждения пользователя.
- Не запускать `rm -rf` и другие необратимые команды без явного подтверждения пользователя и предварительной проверки точного пути.
- Не удалять системные файлы, не менять настройки macOS, не трогать конфигурацию ОС, не завершать системные процессы и не изменять права доступа вне рабочей директории проекта.
- Любое действие за пределами рабочей директории проекта выполнять только после явного подтверждения пользователя.
- Если Sail сообщает, что Docker не запущен, сначала проверить, не вызвана ли ошибка отсутствием доступа к Docker-сокету. Не предлагать запускать Docker и не переходить на локальные PHP, Composer или npm, пока причина ошибки не установлена.

## Стек проекта

- Livewire 4 — серверные интерактивные компоненты.

## Интеграции и инфраструктура

- При реализации и изменении интеграции со СДЭК использовать локальную OpenAPI-спецификацию `docs/openapi_api_v2_integration.json` и официальную документацию `https://apidoc.cdek.ru/`.

## Laravel Boost

- Для задач, зависящих от API, поведения или конфигурации Laravel, Livewire и Filament, сначала использовать Laravel Boost для поиска документации по установленным версиям пакетов.
- Для изучения структуры базы данных использовать Laravel Boost вместо ручного разбора схемы.
- Для диагностики использовать Laravel Boost для чтения последних ошибок, логов приложения и браузера.
- Не записывать новые правила проекта через Laravel Boost без явной просьбы пользователя.
