<project-rules>
# Правила проекта

- Все Markdown-инструкции (`*.md`) всегда писать на русском языке.
- Всегда запускать Artisan команды через Sail: `sail artisan ...`.
- Всегда запускать Composer команды через Sail: `sail composer ...`.
- Всегда запускать npm команды через Sail: `sail npm ...`.
- После изменения кода обязательно запускать форматирование командой `sail composer format`.
- Не использовать Laravel-атрибуты. Конфигурацию классов Laravel задавать традиционными свойствами и методами класса.
- Не дублировать значения и поведение по умолчанию явной конфигурацией, если настройки проекта уже обеспечивают нужное поведение. Это правило относится ко всем настройкам, а не только к дискам хранения файлов.
- Весь пользовательский текст в Blade-шаблонах, включая значения текстовых HTML-атрибутов, оборачивать в хелпер `__()` для последующей локализации.
- Не задавать размеры изображений через HTML-атрибуты `width` и `height`, в том числе у `<img>` и `<source>`. Размеры и пропорции задавать CSS-правилами в основном файле стилей с учётом адаптивности.
- В среде Codex доступ к Docker-сокету может быть запрещён песочницей. В этом случае Sail ошибочно выводит `Docker or Podman is not running`, а `docker info` возвращает `permission denied` для `~/.docker/run/docker.sock`; это не означает, что Docker остановлен.
- Если команда Sail не может обратиться к Docker из-за `permission denied`, повторить необходимую команду с расширенным доступом (`sandbox_permissions: require_escalated`). Не предлагать пользователю запускать Docker и не переходить на локальные PHP, Composer или npm, пока состояние контейнеров не проверено вне песочницы.
- Для безопасной проверки форматирования без изменения файлов использовать `sail composer format:check`; для исправления форматирования после изменения кода использовать `sail composer format`.
- Директория `/template` в корне проекта содержит исходный HTML-шаблон для верстки сайта. Использовать его как основу, переносить нужные элементы в Laravel/Blade/Livewire и адаптировать под требования проекта.
- Всю работу с загрузкой изображений выполнять через `spatie/laravel-medialibrary`.
- Для загрузки изображений в Filament всегда использовать `App\Filament\Forms\Components\MediaImageUpload`.
- Для установки и сброса проекта при необходимости использовать команды `sail artisan project:install` и `sail artisan project:refresh` соответственно. Запускать их только после явного подтверждения пользователя.
- Коммиты в git всегда оформлять по Conventional Commits.
- Текст коммита всегда писать коротко, на русском языке, в повелительном наклонении настоящего времени. Примеры: `feat: создать сущность для акций`, `feat: подключить filament`.
</project-rules>

<architecture>
# Архитектура проекта

- Бизнес-логику определённой области размещать в Service-классах в директории `app/Services`.
- Для типизации входных данных использовать DTO-классы в директории `app/DTO`.
- Конкретную одиночную операцию, которую умеет выполнять система, оформлять как Action-класс в директории `app/Actions`.
- Различать Service и Action по их ответственности: Service содержит логику определённой бизнес-области, Action выполняет одну конкретную операцию.
- Внутри архитектурных слоёв группировать классы по бизнес-сущностям в отдельных директориях, например `app/DTO/Orders/CreateOrderDto.php`, а не в корне слоя.
- Добавлять к именам классов постфикс, отражающий их техническое назначение, например `CreateOrderDto` или `OrderService`.
- В директории `app/Support` хранить `helpers.php` с глобальными функциями и общие сущности, не относящиеся к конкретной бизнес-сущности. Общие трейты, исключения и другие такие сущности группировать в соответствующих поддиректориях.
- PHP Enum размещать в директории `app/Enums` и использовать там, где они уместны.
- Observer моделей использовать для технических системных реакций на жизненный цикл модели, например для сброса кэша.
- Оставлять контроллеры простыми и тонкими: не размещать в них бизнес-логику.
- Не создавать архитектурные слои и сущности для простых случаев, если это только усложнит структуру проекта. Использовать их осмысленно, чтобы сохранять архитектуру простой, чистой и понятной.
- Не добавлять в код поясняющие комментарии, если пользователь не попросил об этом явно.
</architecture>
