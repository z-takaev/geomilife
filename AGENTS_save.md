# Правила проекта

- Все Markdown-инструкции (`*.md`) всегда писать на русском языке.

- Всегда запускать Artisan команды через Sail: `sail artisan ...`.
- Всегда запускать Composer команды через Sail: `sail composer ...`.
- После изменения кода обязательно запускать форматирование командой `sail composer format`.

- Не использовать Laravel-атрибуты. Конфигурацию классов Laravel задавать традиционными свойствами и методами класса.
- Не дублировать значения и поведение по умолчанию явной конфигурацией, если настройки проекта уже обеспечивают нужное поведение.
- Весь пользовательский текст в Blade-шаблонах, включая значения текстовых HTML-атрибутов, оборачивать в хелпер `__()` для последующей локализации.

# Архитектура проекта

- Бизнес-логику определённой области размещать в Service-классах в директории `app/Services`, когда выделение отдельного слоя действительно необходимо..
- Для инкапсуляции запросов и доступа к данным использовать Repository-классы в директории `app/Repositories`, когда выделение отдельного слоя действительно необходимо.
- Для типизации входных и выходных данных использовать DTO-классы в директории `app/DTO`. Создавать DTO только при необходимости, когда это оправдано задачей.

<!-- Подумать над этим правилом -->

- Для подготовки данных к отображению использовать ViewModel-классы в директории `app/ViewModel` в тех случая когда это уместно.
- Конкретную одиночную операцию, которую умеет выполнять система, оформлять как Action-класс в директории `app/Actions`.
- Различать Service и Action по их ответственности: Service содержит логику определённой бизнес-области, Action выполняет одну конкретную операцию.
- Внутри архитектурных слоёв группировать классы по бизнес-сущностям в отдельных директориях, например `app/DTO/Orders/CreateOrderDto.php`, а не в корне слоя.
- Добавлять к именам классов постфикс, отражающий их техническое назначение, например `CreateOrderDto` или `OrderService`.
- В директории `app/Support` хранить `helpers.php` с глобальными функциями и общие сущности, не относящиеся к конкретной бизнес-сущности. Общие трейты, исключения и другие такие сущности группировать в соответствующих поддиректориях.
- PHP Enum размещать в директории `app/Enums` и использовать там, где они уместны.
- В PHP Enum имена case и их строковые значения всегда писать в верхнем регистре, например: `case CREATED = 'CREATED';`.
- Оставлять контроллеры простыми и тонкими: не размещать в них бизнес-логику.
- При передаче данных из контроллеров в Blade-представления использовать хелпер `compact()`.
- Не размещать бизнес-логику в Blade-шаблонах: не выполнять в них бизнес-расчёты, агрегацию данных, запросы и подготовку сложных структур. Передавать в шаблоны заранее подготовленные данные. Допускается простая логика представления, например выбор цвета карточки категории, CSS-класса или отображение элемента по условию.
- Не создавать архитектурные слои и сущности для простых случаев, если это только усложнит структуру проекта. Использовать их осмысленно, чтобы сохранять архитектуру простой, чистой и понятной.
- Не допускать дублирования кода. Если дублирование действительно уместно, заранее предупредить пользователя, объяснить причину и получить его явное подтверждение до внесения изменений.

<!-- Скорректировать правило -->

- Не добавлять в код поясняющие комментарии, если пользователь не попросил об этом явно.
- В моделях соблюдать порядок секций: трейты; константы; свойства конфигурации Eloquent (`$timestamps`, `$table`, `$fillable`, `$hidden`, `$appends`, `$with`); метод `casts()`; метод `booted()`; переопределения поведения Eloquent; связи; query scopes; аксессоры и мутаторы; публичные методы предметной области; методы интеграций; защищённые расширения трейтов; приватные вспомогательные методы.
- В Livewire-компонентах соблюдать порядок методов: инициализация (`boot()`, `mount()`); хуки изменения состояния (`hydrate()`, `updating*()`, `updated*()`); публичные действия; `render()`; завершающие хуки (`rendered()`, `dehydrate()`); защищённые методы конфигурации Livewire (`queryString()`, слушатели, валидация); приватные вспомогательные методы.
- Свойства Livewire-компонентов для полей форм, сохраняемых в Eloquent-модель, называть в `snake_case` в соответствии с именами колонок базы данных, чтобы результат валидации можно было передавать в модель без ручного переименования ключей.

## TDD-цикл (обязательно)

1. Сначала тест: напиши падающий тест и запусти ТОЛЬКО его
   (`./vendor/bin/pest tests/Feature/YourTest.php` или `sail artisan test --filter=YourTest`).
   Убедись, что падает по правильной причине.
2. Запрещено трогать `app/`, `src/`, `database/` до красного теста.
3. Реализация — минимум кода, чтобы тест стал зелёным. Перезапусти целевой тест.
4. Рефакторинг — только после зелёного теста, с повторным прогоном.
5. Полный прогон (`sail artisan test`) — ОДИН раз, как финальная проверка.
   При падении фикси точечно и перезапускай только затронутые тесты.
6. В конце — `./vendor/bin/pint --format agent`. Если Pint что-то поправил,
   прогони полный набор тестов ещё раз.
